## 1. 游戏定位与设计支柱

AnimalCafe 是一款以动物经营咖啡厅为主题的经营游戏。玩家管理动物员工、接待动物客人，并观察由品种、个性、关系、消费能力和人生变化共同产生的互动与故事。

### 1.1 自动经营与主动管理并存

- 咖啡厅在默认状态下可以自动运作。
- 玩家通过点击员工、设备、订单、场景对象和 UI 进行管理。
- 玩家不需要逐个执行所有订单，主要负责观察、调整和处理重要事件。
- 游戏同时支持 Active Mode 与 Idle / Offline Mode，两种模式共享同一套经营状态。

### 1.2 角色驱动的经营世界

- 员工和客人不是只有外观差异的单位。
- Species、Breed、Individual Traits、关系和生活状态会影响行为。
- 客人的经济能力、兴趣和经历会影响点单、消费与故事。
- 系统应让玩家逐渐认识角色，而不是一次显示所有信息。

### 1.3 有策略但不惩罚性过强

- 经营选择会影响效率、客群、利润和发展方向。
- 游戏不设置破产、强制关店或因经营差而 Game Over。
- 经营不佳会减慢成长，但不会删除玩家的咖啡厅或长期进度。
- 系统必须保证玩家能够维持最低收益运营并逐步恢复。

### 1.4 复杂系统保持可读

- 原材料种类保持克制，避免库存管理变成繁琐工作。
- Breed 提供概率倾向，不直接决定角色性格。
- 自动化是默认体验，手动调整用于优化而不是维持基本运作。
- 长期内容可以丰富，但每个系统都应有简单易懂的基础规则。

### 1.5 挂机经营与回访闭环（2026-10-26确认）

AnimalCafe 的核心体验是：**玩家安排经营方向，咖啡厅自行运转；离开一段时间后回来，看到经营成果与角色变化，作出新的选择，再放心离开。** 玩家不负责逐单点单、制作、送杯或清理。

```text
安排菜单、员工与经营方向
→ 咖啡厅自动服务，积累收益、角色经历与经营记录
→ 玩家回来查看成果、经营问题与值得关注的角色变化
→ 作出经营或故事选择，把成果投入家具、设备与店铺成长
→ 观察调整效果，或者欣赏动物工作与店铺生活
→ 带着下一次回访的期待离开
```

**一次回访的玩法。** 查看简短摘要，了解哪些商品受欢迎、哪里效率较低、哪些熟客来过或角色故事有后续；选择调整菜单、员工安排或补货策略；用积累的资源装修、升级或解锁。玩家可以只完成其中一项，也可以长时间观察、装修或研究经营，不要求每次清空全部待办。

**三种时间尺度。** 前台几分钟内应能看见订单完成、状态变化和管理调整的反馈；离开数小时可以获得有意义的积累；更长时间通过店铺成长、经营路线和角色关系形成目标。普通回访约 3～10 分钟是初始体验目标，不是在线时长要求或不可修改的平衡参数。长营业周期不能变成第一次进步或第一次获得反馈的等待门槛。

**主动选择有意义。** 自动化负责基本运转，玩家决定经营方式。例如平价高周转、精品菜单、不同员工组合和店铺布局应产生可理解的取舍。示例不是已经批准的数值效果。避免只有一套明显最优配置，也不要求玩家持续手动干预才能维持基本营业。

**长期吸引力。** 店铺成长提供可见进步和收益消费出口；稳定的员工、回头客、关系与人生变化提供情感联系。两者共同支持回访，不能只靠数字膨胀或重复点击领取维持循环。角色陪伴与经营优化的最终比重仍待试玩与 Owner 选择，不把其中一种玩家偏好视为已经确定。

**让玩家放心离开。** 不把手动开店、确认报告、点击下一天、逐单操作或逐笔领取收益设为正常经营前提。重大故事可以暂存，等待玩家选择时其他经营继续；不因错过上线时间永久丢失关键故事。普通经营问题尽量在已配置且安全的规则内自动处理，不能通过频繁上线补库存、确认小事或解除普通等待来维持基础循环。

**真实故障与恢复。** 挂机目标不能成为瞬移、穿人、虚构完成订单、忽略库存或伪造收益的理由。真实无路、缺设备或业务失败仍需明确 `Blocked` 或失败事实；局部故障尽可能不停止无关且有效的服务。现有 P11–P14 的有界恢复、路径保护和显式恢复继续有效，长期无人值守策略尚需设计，不宣称现有实现已经能够自动解决所有故障。

**离开后仍能成长。** 目标体验同时覆盖前台观察、后台／挂起以及退出后再回来；不以持续渲染 Scene 或玩家一直开着游戏作为进步条件。第 5 节定义离线语义，具体结算仍受真实资源、有效服务能力、已批准时间上限与故障边界约束。

**不作为核心体验的内容。** 逐杯 QTE、反复派发普通订单、强制整点回访、收益必须点领取、报告未读就停店、短周期缺货迫使补货，以及闭店期间禁止查看或装修，都不应成为基础玩法。手动干预只能作为可选优化，不把操作频率直接变成主要收益来源。

**未来配置生效。** 某些经营配置可以延后至下一次闭店等安全边界生效，并清楚显示当前值、待生效值与生效时机；具体哪些配置采用此方式，进入相关功能前再确认。不把全部设置一律推迟，既有 Syrup Add-on「下一杯生效」规则也不被本段覆盖。

本节是长期产品方向，不能代替每个 Phase 的 spec、implementation plan、技术验证或 Owner manual acceptance。已完成系统的变更必须先说明受影响文件、rework、数据兼容风险与 regression；没有因为本次文档更新而自动获准重写或删除。

## 2. 玩家操作、Camera 与时间

### 2.1 操作方式

- 游戏没有可移动的玩家角色。
- 玩家使用点击和 UI 下达管理指令。
- 正式玩家操作以 Android / iOS Touch 为主，不依赖 Hover、精细 Mouse 或 Keyboard。
- Windows Mouse 只用于 Unity Editor 开发、自动化 fixture 和人工验证，不形成独立的 Windows UX 或 release requirement。

2026-10-27 Owner 明确：**MainCafe 只呈现已接入的正式玩家功能与玩家界面。** 开发用黑色诊断 HUD、Epoch／订单 ID／内部任务状态等详细数据放在独立 Validation Scene，不作为正式 Main UI。营业阶段、倒计时、设备未就绪和真实受阻提示属于玩家需要的信息，应使用现有正式 UI 风格和玩家可理解的文案；不能为了隐藏诊断面板而移除营业逻辑或掩盖故障。验证用短时配置与自动测试布局不得带入正式 Main。

### 2.2 Camera

采用类似《暗黑破坏神》的固定斜俯视角（固定 3/4 Isometric-like Camera）：

- Camera 不能旋转。
- 支持放大和缩小。
- Android / iOS 使用单指拖动平移，并使用 pinch 控制连续缩放。
- Unity Editor 可以保留 Mouse drag / wheel 作为开发测试映射，但必须复用同一 Camera rules，不能形成第二套 gameplay behavior。
- Camera 移动边界和缩放上下限根据场景布局设置。

### 2.3 游戏速度

基础时间控制包括：

- Pause
- `1x` 正常速度
- `2x` 加速

Pause 用于查看角色、订单和经营信息，`2x` 用于缩短等待。是否允许在 Pause 状态下继续下达管理指令仍待确认。

2026-10-26 Owner 已确认：**营业周期使用独立现实经过时间，营业 8 小时，实际排空后休息 2 小时；Pause／2x 只影响 Scene 角色、制作、移动与动画，不改变周期时间。** 装修自动 Pause 同样不停止周期；Closing 仍须等真正排空，因此暂停或堵路可能延后休息起点。当前 P0–P14 的 Scene 暂停与加速合同保留。P15 实现运行中的周期协调，应用挂起／退出后的持久化与收益结算由后续 Save／Offline 实现，不把独立时钟批准当成离线系统已完成。

### 2.4 角色移动与受阻恢复

- Customer 与 Employee 从当前位置步行到目标；遇到其他角色会避让或等待，不能整个人互相穿过，也不能穿墙或实体家具。
- 保留 Shiba / Westie 约 1.30 m 的原模型尺寸。到达、转身、避让时短暂轻微的身体边缘、手臂或尾巴穿插可接受；持续明显嵌入实体不可接受。原 Interaction Anchor 优先，不统一强制向外偏移。
- 起点无效时返回明确失败，不把角色挪到附近 NavMesh，不使用瞬移或销毁重生恢复。目标只能在原站位区域、同柜台侧做有限采样。
- 连续受阻后只从当前位置重新寻路一次；仍无法到达时，可以步行去已配置且可达的 recovery point，否则报告失败，不能无限重试。
- Pause 同时停止位移、walk 与等待计时；2x 同时作用于它们。walk 根据实际位移播放，受阻停下时不持续原地走。
- 停用角色时立即停止移动、转向和当前请求；仍存在的身体保留位置占用，重新启用后需从实际位置验证新请求，不自动挪动角色。
- 装修 Confirm 前检查实体家具与暂停角色的身体范围，冲突时保留 Preview 并拒绝确认。正式布局变化使旧路径失效；退出前重新验证必要服务组合和路径。
- 必要服务路径失效时允许保留装修，但保持暂停并显示“路径被挡住了，请进入装修调整。”；时间按钮不能绕过。修复通过后恢复装修前速度，保留玩家明确选择的 Pause；非必需 station 局部不可用不阻塞仍完整有效的服务组合。

> 2026-10-30 **已批准、实施中**：[服务交通协调与Regression](superpowers/specs/2026-10-30-service-traffic-coordination-design.md)。Owner已批准“保留NavMesh＋统一顾客／员工交通承诺＋必要通路与等候位限制”的开发及测试；区分普通拥堵、安全等待与真实Blocked，保留付款／FIFO／容量和实际到站规则。[实施计划](superpowers/plans/2026-10-30-service-traffic-coordination.md)按原Main反例、共同许可、逐入口迁移及regression执行；批准不代表改造已完成或新源已验收。

## 3. 核心经营循环

### 3.1 基础服务流程

咖啡厅在店面较小、没有座位时，采用先付款的外带模式：

```text
客人进入咖啡厅
→ 在柜台点单并付款
→ 前往 Pick-up 点等待
→ 员工制作商品
→ 客人在 Pick-up 点取走商品
→ 客人离开咖啡厅
```

这套流程是所有店面都可以使用的基础服务方式，不依赖座位、桌边点单、送餐或清理桌面。

外带订单在对应的正确客人实际取走商品后才进入 `Completed`（已完成）状态。商品制作完成并送达 Pick-up 后，订单处于等待取餐状态；客人取走商品后即可完成订单，无需等到客人离开咖啡厅。

当咖啡厅扩大并增加座位后，系统应保留扩展更多服务流程的空间，例如：

- 客人仍可选择基础外带流程。
- 客人点单后入座等待。
- 员工将完成的商品送到桌边。
- 客人用餐后离开。
- 员工清理桌面，使座位可以再次使用。

座位不应完全取代 Pick-up 外带流程。未来可以让外带与堂食同时存在，并由店面布局、客人偏好、订单类型或经营策略影响客人的选择。

堂食是否在柜台先付款、是否允许桌边点单、座位分配和清理规则尚未确认，应在设计堂食功能前单独决定。

### 3.2 订单与员工

- 空闲员工自动领取等待中的订单。
- 默认按照点单顺序处理，即 FIFO（First In, First Out）。
- 玩家可以在不进行持续操作的情况下观察经营。
- 调整订单优先级和为订单指定员工属于可选扩展。
- 即使加入手动调整，自动处理仍应是默认规则。

#### 已确认的固定岗位工作规则（2026-10-14）

- Cashier 在顾客使用的 Cash Register（CR）Employee Side 待命，服务耗时 2 个游戏秒；Barista 在 Coffee Machine（CM）的 `+Z` Employee Anchor 待命，制作耗时 3 个游戏秒，工作时播放 working。
- Barista 制作后手持杯走到 Pick-up；下半身使用实际移动的 Walk，上半身保持 Carry。到达后立即放杯，交付成功，再空手步行返回 CM；实际返回之前仍忙，不能接第二个任务。
- 每个绑定的 table module / Surface Slot 最多显示三杯，按家具局部坐标呈三角形排列。第四杯及之后仍可交付；这是视觉展示上限，不是订单库存或顾客容量限制，轻微杯子穿模可接受。
- 每名员工同时只拥有一个任务。Cashier 与顾客绑定同一个选中的 CR；CM / Pick-up 按稳定顺序选择具备完整往返路径的有效组合，不在同一任务中临时换目标。
- Pause 冻结制作计时、移动与动画；`2x` 使用统一游戏时间。装修未确认修改时继续原任务；确认正式修改后退休旧任务、清理未交付的手持杯，保留员工身份、岗位与身体，从实际位置重新验证并步行回位。缺失设备或无路可达时明确 Blocked，修复后通过恢复入口重试，不瞬移或重新生成员工。
- 已放下的杯子归属原正式 Surface Slot，随支撑家具移动和旋转；只有对应 Pick-up / Slot / 支撑失效才清理该处展示。返回失败或取消不能撤回已经成功放下的杯子。

Phase 13 先用受控任务验证以上规则；真实顾客服务、付款、订单与取杯整合属于 Phase 14。技术执行与验收状态见 [P13 Validation Report](Phase13_Validation_Report.md)。

#### 已批准的P14整合规则（2026-10-19，2026-10-20追加顾客持杯与多侧取餐，2026-10-21同步验证边界）

以下规则用于真实Customer／Order整合模式；上面的P13受控派单仍保留独立验证入口。实现与验收状态见 [P14 Validation Report](Phase14_Validation_Report.md)，操作见 [P14 Beginner Guide](Phase14_Beginner_Guide.md)。

### 3.3 商品可用性与材料预留

- 客人付款前，系统检查商品所需材料是否可预留，并确认店内存在可运行的必要设备。
- 设备当前正在处理其他订单时，新订单仍可进入 FIFO 队列，不要求设备立即空闲。
- 无法制作的商品不能被点单。
- 客人只从当前可制作的菜单中选择商品。
- 付款成功时，系统立即为订单预留材料。
- 员工开始制作时，预留材料转为正式消耗。
- 已被订单预留的库存不能被其他订单重复使用。
- 如果未来允许取消订单，未使用的预留材料应退回可用库存。

付款后如果设备或路径暂时失效，订单保持等待状态，不重复收费，也不丢失已预留材料。长期无法恢复时如何退款、取消或替换商品仍待确认。

### 3.6 自动 Save

游戏采用自动 Save，不提供需要玩家管理的手动 Save 流程。

- Save 失败不能破坏最近一份有效存档。
- 具体保存字段、频率、备份和恢复方式由 implementation plan 定义。

### 3.7 最低收益保底

当玩家资金或库存状态很差时，系统仍保证基础运营：

- 每个营业日提供少量基础供应。
- 基础供应只能用于指定的低利润基础咖啡。
- 基础供应不能囤积，也不能直接出售。
- 该机制只保证最低收益，不代替正常采购和经营。
- 每日数量、基础配方和利润属于后续经济平衡参数。

社区补助或恢复任务可以作为正向事件，但不能以重新开始作为惩罚。

## 4. 角色与 NPC 系统

### 4.1 角色个性结构

每个角色的行为由多个因素共同决定：

```text
Species 倾向
+ Breed 倾向
+ Individual Traits
+ 当前心情
+ 双方关系
+ 咖啡厅环境
= 本次互动结果
```

#### Species（物种）

Species 提供宽泛行为倾向。例如，猫可能更重视私人空间，狗可能更容易参与群体互动。

#### Breed（品种）

Breed 提供更具体的概率倾向。例如：

- 柴犬可能更容易生成固执、独立等 traits，因此发生争执的概率略高。
- 金毛可能对其他物种较友善，但与部分狗相处时更容易产生竞争。

Breed 不能成为绝对性格。同一 Breed 的两个角色仍会因为 traits、心情、关系和经历而表现不同。

#### Individual Traits（个体特性）

可能的 traits 包括：

- Friendly（友善）
- Short-tempered（易怒）
- Patient（耐心）
- Competitive（好胜）
- Shy（害羞）
- Hardworking（勤奋）
- Lazy（懒惰）
- Clean（爱干净）
- Foodie（贪吃）

正式 traits 清单、组合规则和数值尚未确定。

### 4.2 Traits 的发现

- 明显 traits 会在角色资料中显示。
- 隐藏 traits 通过工作、对话、冲突和重复来访逐渐发现。
- Traits 的发现既服务经营判断，也服务玩家与角色建立感情。

### 4.3 角色互动

系统支持：

- 员工与员工
- 员工与客人
- 客人与客人

负面互动可以包括争吵、心情下降、服务效率降低和声誉影响。

正面互动可以包括互相帮助、效率提升、安慰客人、满意度提升，以及特殊对话、奖励或故事事件。

### 4.4 Character ID 与角色资料

每位 NPC 都拥有稳定的 `Character ID`。

较稳定资料包括：

- Species 和 Breed
- 外观
- Individual Traits
- 基础喜好与厌恶

动态状态包括：

- 当前心情
- 职业与收入
- 人生阶段
- 消费预算
- 价格敏感度
- 品质偏好
- 与其他角色及咖啡厅的关系
- 近期事件与故事进度

### 4.5 动态身份与人生变化

同一个角色可以保留过去的关系和经历，同时改变职业、收入和消费能力：

```text
学生
→ 毕业
→ 初入职场
→ 收入与消费等级提高
```

其他可能事件包括找到工作、升职、失业、个人破产、结婚、离婚、搬家或退休。这里的“个人破产”只描述 NPC 的人生事件，不代表玩家咖啡厅会破产或 Game Over。

身份变化会影响预算、商品选择、来店频率与故事，但不能完全决定角色行为。

### 4.6 客人生成与个人故事

NPC 内容由两层组成：

- 随机生成的普通客人，提供日常变化。
- 拥有连续故事的特殊客人，提供更明确的角色线。

系统设计应允许普通客人成为回头客，并逐渐积累喜好、关系和经历。长期个人故事不要求全部手写，可以由 traits、关系、记忆和事件组合产生。

### 4.7 Active Mode 事件

- 普通互动可以自然发生。
- 重要互动向玩家展示事件并提供处理选择。
- 选择可以影响心情、关系、声誉和后续故事。

示例：

```text
一名员工与客人发生争执：

A. 立即介入调解
B. 让另一名友善员工处理
C. 暂时不干预
```

### 4.8 消费行为

NPC 的购买意愿由多个因素共同决定：

```text
消费层级
+ 可用预算
+ Individual Traits
+ 商品兴趣
+ 与咖啡厅的关系
+ 商品价格与稀有度
+ 当前人生状态
= 购买意愿
```

- 低消费层级通常更重视价格与实用性。
- 中等消费层级会在价格、品质和个人喜好之间权衡。
- 高消费层级更可能考虑 Premium 或限量商品，但不会自动购买。
- 高收入但节俭的角色可能拒绝昂贵商品。
- 收入不高但喜欢咖啡厅的角色也可能为限定商品存钱。

## 5. Idle / Offline Mode

当游戏不在前台时，不要求游戏持续实时运行。系统记录玩家离开的时间，并在玩家回来时计算 offline progression。

### 5.1 基础行为

- 普通经营和小事件在有效服务、资源与已批准规则内自动推进；不能把前台仍为 `Blocked` 的旧订单直接改写为完成。
- 小型互动由 traits、关系和咖啡厅状态自动处理。
- 重要故事事件不会阻塞其他经营。
- 玩家返回后查看简短的离线经营报告。
- 报告记录值得关注的事件，例如争吵、回头客到访或隐藏 trait 被发现。

### 5.2 重大事件

- 重大故事事件可以暂存。
- 玩家返回后亲自选择处理方式。
- 事件等待期间，咖啡厅其他部分继续经营。

### 5.3 经营方针

可选的自动管理扩展包括：

- 优先安抚客人
- 优先保护员工
- 优先维持经营效率

系统可以根据玩家预设方针处理离线期间的重要事件，让挂机管理具有策略性。

### 5.4 自动跨日与一致性（2026-10-26确认）

- 挂机包括前台不操作、后台／挂起和退出后返回三种场景；产品规则保持一致，技术执行方式不要求相同。
- 离线返回应按离开期间的营业、收尾与休息边界推进，可以跨越多个正常周期；不在第一次打烊或未读日报处等待玩家点击。可结算时长仍受尚待批准的 Offline cap 限制，自动跨日不代表无限收益。
- 休息期间不产生正常接待收益。必须扣除休息时间，处理既有订单与资源边界，不能把全部离开时间按满负荷营业计算。
- 重复切前后台、重启或重读报告不能重复结算、重复创建故事、重复增加天数或重复应用待生效配置。
- Offline summary 复用相同商品、库存、付款、有效服务能力与角色规则，不要求逐帧重放所有 Scene 角色、NavMesh 路线和动画。
- 不把纯表现故障等同于业务丢单；也不以摘要模拟掩盖真实无效布局、库存不足或无法履约。具体降级、恢复和结算边界仍待对应 spec。

### 5.5 玩法验证目标与开发边界

长期试玩应检查：玩家离开后能否继续正常成长；回来时能否迅速理解变化并找到一个有意义的选择；普通经营是否依赖频繁回访；故事是否不会因未及时上线而丢失；经营选择与装修是否产生可理解的结果。

最小验证只需要基础商品、营业周期、真实收益与 Save；不应等全部远期内容完成才第一次验证「离开—返回—查看结果—调整」。Owner 已于 2026-10-26 指示按审查结论调整路线：提前验证安排见 Roadmap 4.2、P18A 与 P20A。该路线批准不代替各阶段具体 spec／plan approval，也不意味着已实现完整 Offline 系统。

## 6. 商品、材料与库存

### 6.1 商品类别

#### Coffee（咖啡饮品）

- 基础咖啡
- Latte 等常见品类
- 通过 Coffee Beans 和 Syrup Add-on 产生差异的饮品

#### Bakery（烘焙商品）

- 不同种类的面包和甜点
- 平价与 Premium 策略可以影响 Bakery 的商品方向

#### Merchandise（周边）

- 咖啡杯、玩偶、贴纸或其他主题商品
- 主要通过进货获得，不要求玩家制作
- 客人的收入、兴趣、traits 和关系影响购买意愿

#### Packaged Coffee Beans（包装咖啡豆）

- Coffee Beans 既是饮品原材料，也可以包装后出售。
- 玩家需要在制作饮品与出售整包 Coffee Beans 之间分配库存。

### 6.2 基础原材料方向

原材料数量应保持克制：

- Flour（面粉）
- Egg（鸡蛋）
- Milk（牛奶）
- Coffee Beans（咖啡豆）
- Syrup（通用糖浆库存）

```text
Milk ─────────→ Coffee 与 Bakery 共用
Coffee Beans ─→ Coffee 或包装出售
Syrup ────────→ 安装 Add-on 后制作风味 Coffee
Flour ────────→ Bakery
Egg ──────────→ Bakery
```

Milk 作为 Coffee 与 Bakery 的共用资源，可以产生库存分配选择。

Cream 是否作为独立材料仍未确定。

## 7. Coffee Bean 探索系统

### 7.1 系统目标

Coffee Beans 不只是普通进货材料。玩家可以派员工进行一段时间的探索，随机发现不同 Coffee Beans。

Coffee Beans 可以具有：

- 名称或产地主题
- 品质
- 稀有度
- 1–2 个风味 traits
- 适合的咖啡类型
- 制作价值与包装售价

示例：

```text
晨雾豆
品质：Rare
风味：Fruity、Light
适合：Iced Coffee
```

### 7.2 探索取舍

- 被派去探索的员工暂时不能参与咖啡厅工作。
- 探索结束后随机发现 Coffee Beans。
- 发现的 Coffee Beans 可以制作饮品或包装出售。
- Coffee Beans 可以进入收藏图鉴。
- 员工 traits 可以作为影响探索结果的候选规则。

系统不需要模拟复杂的现实咖啡知识，应保持“品质 + 少量风味 traits”的可读结构。

### 7.3 Coffee Machine 配置方向

- 每台已摆放的 Coffee Machine 独立保存当前选择的 Coffee Bean。
- 正常经营中点击 Coffee Machine，通过 Bottom Sheet 查看和更换 Coffee Bean，并显示该 Coffee Bean 的剩余库存；不显示“今日已使用”。
- Coffee Machine 配置面板打开时，经营与 NPC 行为继续运行，不进入 Decoration Mode。
- Coffee Machine 正在制作饮品时修改配置，当前饮品继续使用旧配置，新配置从下一杯开始生效。
- 本节记录未来 Coffee Bean gameplay 的已确认 UX 方向，不要求 Phase 5 提前实现 Coffee Bean inventory、selection 或 Save logic。

## 8. Syrup 与 Add-on 系统

### 8.1 通用 Syrup 库存

所有风味共用一个 Syrup 库存：

```text
Syrup：24 / 30 杯
```

- 任何使用 Syrup 的饮品统一消耗 1 点。
- 风味 Add-on 不建立独立库存。
- Add-on 不会在制作饮品时被消耗。

### 8.2 Add-on 插槽

```text
Syrup System
├─ Slot 1：Lychee Add-on
├─ Slot 2：Pistachio Add-on
└─ Slot 3：未解锁
```

- Add-on 和插槽数量通过游戏进度逐渐解锁。
- 已装备 Add-on 会启用对应风味。
- 正常制作时，玩家从已装备 Add-on 中选择一种风味。
- 结合 1.5 的挂机方向，上述选择应通过菜单／设备配置或可选管理操作表达，不能要求每杯手动选风味才继续制作；具体自动选取规则仍待相关 gameplay spec。
- Add-on 是永久配置资源，不需要水果或糖等额外材料。
- 每台 Coffee Machine 独立保存自己的 Syrup Add-on Slot 配置。
- 已解锁的 Slot 可以留空；未解锁的 Slot 保持锁定并清楚显示解锁状态。
- Coffee Machine Bottom Sheet 显示全店共享的 Syrup 剩余库存，例如 `24 / 30`，不显示“今日 Syrup 用量”。
- Coffee Machine 正在制作饮品时更换 Add-on，当前饮品不变，新配置从下一杯开始生效。
- 本节记录未来 Syrup & Add-on gameplay 的已确认 UX 方向；正式 inventory、slot equip / replace、Save / Load 和 flavored drink behavior 仍由对应 gameplay Phase 实现。

### 8.3 特殊融合饮品

特殊事件可以暂时允许多个 Add-on 融合：

```text
Latte + Lychee + Pistachio
→ Festival Fusion Latte
```

首次发现后，融合饮品保留在配方图鉴中，但只能在对应节日或特定条件下再次制作。

## 9. 经营策略系统

### 9.1 Strategy Track

经营策略类似动作游戏中的 skill tree 或 build。投入方向会改变：

- 吸引的客群
- 菜单结构
- 商品价格
- 可使用设备
- 服务速度
- 原材料需求
- 咖啡厅整体风格

### 9.2 平价经营

- 面向普通居民、学生、低收入工作者和价格敏感客人。
- 价格较低、客流较大、单笔利润较低、周转较快。
- 设备投入较少，可以使用 Brewer 或自动咖啡机。
- 不强制依赖特殊 Coffee Beans。
- Bakery 偏向普通、便宜和容易量产的商品。
- 经营重点是效率、库存控制与快速服务。

### 9.3 Premium 经营

- 面向重视品质的客人、咖啡爱好者和较高消费群体。
- 客流可能较少，但单笔利润和客人期望较高。
- 重视 Coffee Beans 的品质与风味。
- 可以使用 Grinder、Espresso Machine 和手冲设备。
- Bakery 可以发展精致甜点和限定商品。
- 设备、员工技能和原材料投入更高。

### 9.4 混合 Build

- 平价与 Premium 路线不永久互斥。
- 玩家可以主修一条路线，同时投资另一条。
- 可以形成社区平价店、精品咖啡店或带少量 Premium 招牌商品的混合经营。
- Strategy Track 影响客群出现概率，但不会完全禁止其他客群进入。
- NPC 的收入、价格敏感度、品质偏好、traits 和人生状态共同决定其反应。

## 10. 店铺扩建与装修系统

### 10.1 系统目标

店铺扩建与装修是一个完整的长期系统，同时承担三种作用：

- **成长线**：咖啡厅从小店逐渐发展为更大的店面、特殊区域和双层空间。
- **经济循环**：为经营收益提供持续、有意义的消费出口。
- **个性表达**：让不同玩家的 Animal Cafe 呈现不同布局、主题和风格。

扩建不能只是增加空白地图面积。新空间应能够提高经营容量、支持更多设备和员工，或解锁新的服务区域。

### 10.2 整体 Grid 与扩建

整个店铺拥有一个统一的可装修 Grid：

```text
当前可装修面积 = n × m
```

- `n × m` 表示整个店铺当前可使用的装修面积，不是某个工作站的局部区域。
- 玩家只能在已解锁的 Grid 中摆放家具和功能。
- 扩建消耗经营资源，并增加可装修面积。
- 家具、结构部件和特殊区域也会随成长逐渐解锁。

扩建采用混合方式：

- 普通店面通过矩形 Grid 区块扩大。
- 后厨、二楼、露台、VIP 区等特殊空间通过预设区域解锁。
- 特殊空间解锁后，内部仍允许玩家自由装修。
- 楼层连接和特殊区域入口保持受控，确保 Pathfinding 与场景结构稳定。

扩建可以增加：

- 可摆放面积
- 桌椅和顾客容量
- 工作站和员工容量
- Bakery、Merchandise 或动物互动等功能区域
- 猫咪休息室、VIP 区、露台等特殊空间

### 10.3 家具分类

装修内容分为：

#### 结构类

- 地板
- 墙纸和墙裙
- 门窗
- 楼梯
- 隔断

#### 功能家具

- Cash Register
- Coffee Machine
- Grinder
- 展示柜
- 桌椅
- 工作台

功能家具可以影响容量、效率、可制作商品或可用服务。

#### 装饰家具

- 沙发
- 书架
- 植物
- 灯具
- 玩偶
- 挂画
- 菜单板
- 照片墙
- 时钟
- 地毯和脚垫

纯装饰主要服务个性表达和整体 Atmosphere，不应让玩家为了单件最优数值被迫使用不喜欢的家具。

#### 主题套装

可能的主题包括森林、日式、复古、海边、圣诞或特定动物主题。主题可以影响整体 Atmosphere、特定客群或特殊事件，但具体规则尚未确定。

### 10.4 室内墙面与结构编辑阶段

室内墙体采用分阶段实现：

- 早期店面使用固定墙体，不允许玩家建造、移动或删除墙。
- 初始店面使用 `8 × 8` Floor Grid；固定 Camera 下只显示 Back-left 与 Back-right 两面墙，靠近 Camera 的两侧保持开放显示，但 Floor Layout Bounds 仍限制家具不能摆到店外。
- 玩家可以选择兼容的墙面或地面区域，更换 Paint、Wallpaper、Wainscoting 和 Floor Surface。
- Wall Decoration 可以吸附到兼容墙面，并跟随稳定 Surface ID 保存位置。
- 每面初始墙使用独立 `Wall Slot Grid`：水平方向 8 columns、垂直方向 2 rows，每个 Slot 为 `1 m × 1 m`；下层从地面上方约 `0.5 m` 开始，上下两层分别约高 `1 m`。
- Window 在早期版本中作为固定方向的 Wall-mounted object 使用 `Wall Footprint`，可占上层或下层 Slot，并与挂画等 Wall Decoration 共享 occupancy；同一 Slot 不能重叠，物品不能跨墙角，也暂时不能自由旋转。
- 初始店面在 Back-right Wall 下层中央附近放置一个 `1 × 1` Window；后续玩家可以移动、增加或移除 Window。真正切割 Wall geometry 的 Door / Window Opening 属于后期高级结构编辑。
- 初始 Entrance 位于靠近 Camera 的开放边界中央，以稳定 Entrance ID 和清楚的简单光线或地面标记表示；入口内侧 `2 × 2` Grid 是可行走但禁止家具占用的 Entrance Clearance Zone。
- Preview 不直接修改正式 Layout；只有确认后才提交 Surface appearance change。
- Camera 或墙体遮挡时，Decoration Mode 应提供可读的编辑显示，例如临时隐藏、淡化或切换墙面显示；具体表现由对应 Phase design 确认。

Store Expansion 稳定后，系统可以再加入高级结构编辑：

- 建造、移动或删除墙
- 调整房间边界
- 放置、移动真实 Door / Window Openings；早期 wall-mounted Window 继续由 Wall Slot occupancy 管理
- 重新计算 Room、Surface、Grid Occupancy、NavMesh 和营业 readiness

高级结构编辑不能静默破坏现有家具、Wall Decoration、功能路径或 Save。发生冲突时必须指出受影响对象，并要求玩家修复或取消修改。

### 10.5 Grid 自由摆放

家具采用 Grid-based 自由摆放：

- 家具可以在已解锁区域内移动。
- 家具可以按允许角度旋转，基础方向为每次 `90°`。
- 家具拥有自己的 Grid Footprint。
- Wall Decoration 吸附到兼容墙面。
- 地板和墙面材质按对应表面或区域更换。
- 家具不能与墙体、其他实体家具或未解锁区域非法重叠。

“自由摆放”不代表功能家具必须使用固定形状或固定位置。玩家可以用长 Counter、小桌子、岛台或多件家具组合出自己的服务布局。

Counter 使用明确的 modular contract：

- `1 × 1 Counter Module` 始终是独立 Furniture Instance，提供一个 `1 × 1` Surface Slot；多个相邻模块不会自动合并。
- 正式 `1 × 3 Counter` 是一个完整 Furniture Instance，整体移动和旋转，并提供三个独立的 `1 × 1` Surface Slots。
- Surface Slots 由 Prefab 中明确的 local markers 定义，不根据 Floor Footprint 或 Model bounds 自动猜测；相同 `1 × 3` Footprint 的 Sofa 可以完全没有 Surface Slot。

### 10.6 功能家具与自动 Interaction Anchors

家具种类先决定 gameplay function，Prefab 的明确方向或 markers 只负责说明功能发生在哪里；普通家具不需要无关的 Interaction markers。

- Coffee Machine 的 Function Type 明确标识其功能，设备 `+Z` 正面是员工 Interaction Side，不需要 Customer Side。
- Cash Register 的 Function Type 明确标识其功能，并必须提供互相相反的 Employee Side 与 Customer Side。
- Coffee Machine 与 Cash Register 都可以在一个 Surface Slot 上按 `90°` 旋转；方向数据随设备旋转，但不改变支撑家具的 Floor Footprint。

以放置在桌面或 Counter 上的 Cash Register 为例，系统自动计算：

- 员工操作位置
- 客人点单位置
- Order Queue 的起点和延伸方向

玩家可以移动或旋转 Cash Register 及其支撑家具。Interaction Anchors 会随位置和朝向重新计算。

Order Queue 不要求玩家手动逐格设置。第一位顾客的 Interaction Position 固定在 Cash Register 的 Customer Side；Queue 从该位置向远离 Cash Register 的方向开始，后续队伍可按确定性规则转弯绕开障碍。Employee Side 位于相反方向，不参与 Queue 初始方向。

系统验证：

- 员工能否到达操作位置
- 客人能否到达交互位置
- 入口、服务点、Pick-up 与出口之间是否存在有效路径
- Interaction Position 是否被墙体或家具阻挡

家具不需要被定义为永久的“Counter”。经营功能由具体设备、可用表面、Interaction Anchors 和路径共同形成。

### 10.7 玩家设置的 Pick-up Point

Pick-up Point 是当前需要玩家主动决定的主要 Interaction Point。

- Pick-up Point 必须绑定到桌子、Counter、架子等兼容商品表面。
- 玩家可以选择该家具占用范围内的有效 `1 × 1` Surface Slot。
- 一个 `1 × 1 Counter Module` 只有一个主要 Surface Slot；一个正式 `1 × 3 Counter` 有三个可独立使用的 Surface Slots。Cash Register、Coffee Machine 或 Pick-up Point 各使用一个主要 Slot。
- Ceramic Cup 等制作过程中的商品视觉可以短暂出现在设备或 Pick-up 表面，但不作为永久家具占用整个 Surface Slot。
- Pick-up Point 使用相对家具的局部位置保存；移动或旋转家具时，Pick-up Point 随家具一起移动。
- 系统自动生成员工交付位置和客人取餐位置。
- 员工把完成的商品送到绑定表面。
- 客人到达相邻位置后取走商品。
- 员工与客人可以在调度允许时共用同一个相邻 Interaction Position，也可以使用不同位置。
- 如果不存在可用的交付路线或取餐路线，该 Pick-up Point 无效。
- Pick-up Point 同时作为 Pick-up Queue 的首个服务点，队伍从该位置自动向后延伸。

这允许玩家使用小桌子、长柜台、独立货架或其他兼容家具作为 Pick-up 区，而不要求固定的柜台方向。

### 10.8 Placement Validation 与 Pathfinding

系统在确认布局前检查：

- 家具是否位于已解锁区域
- 家具是否重叠
- 必需的 Interaction Anchors 是否可用
- 入口、Cashier、Pick-up 和出口是否连通
- 员工是否能到达工作设备
- 顾客是否能完成当前启用的服务流程

如果布局无效，游戏应指出具体原因和问题位置，不能只显示模糊的“无法摆放”。

### 10.9 Decoration Mode

玩家可以随时进入 Decoration Mode：

- 正常经营 HUD 提供独立的 Decoration 入口；Coffee Machine 的经营配置面板不提供移动、旋转或收起家具操作。
- 进入 Decoration Mode 时自动 Pause。
- 玩家可以移动、旋转、放置或收起家具。
- Decoration Mode 统一承载 Floor Furniture、Wall Decoration 和兼容 Surface Slot 上的 Pick-up Point 编辑；各能力仍按对应 development Phase 分阶段实现。
- 编辑过程中暂停 NPC 行为，避免 Pathfinding 状态不断变化。
- 2026-10-07 Owner确认：正常完成有已确认修改的Decoration后，结束旧顾客批次，清理其角色、移动请求、排队与容量，再在新布局可营业时按随机到店间隔重新入店。只打开再关闭、取消未确认Preview不重置顾客。员工使用独立生命周期，保留角色、身份与岗位，不参与顾客清理；具体工作恢复按员工任务规则确定。未完成订单的业务处理另在Coffee Loop实现前确认，不推定退款/付款规则。
- 2026-09-12 P8R 获批规则：切换到另一个装修分类 Tab 时，先取消当前未确认 Preview，再进入目标分类；不自动保存，已确认 Layout 不变。2026-10-04 补充：重复点击当前 Tab 时，若 Catalogue 已收起则展开，已展开则保持；保留 Preview、target、已确认 Layout 和目录浏览位置。Store / Exit 确认弹窗仍独占输入。跨 Tab 取消时同时终止旧拖拽，不能将旧 pointer 的后续动作带到新分类。
- 退出前重新验证布局、Interaction Anchors 和路径。
- 玩家可以保留尚未完成的装修，但在必需服务路径无效时不能开始或恢复营业。
- 非必需功能的布局无效时，对应功能明确标记为不可用，不阻塞其他有效区域。

### 10.9.1 Phase Scope Discipline

- 当前 development Phase 只设计、批准和实现该 Phase 明确列出的 scope。
- 探索中提前确认的未来 UX 或 gameplay 方向可以记录为 Future Feature Concept，但不自动成为当前 Phase deliverable，也不授权提前实现。
- Phase 5 只提取通用 Design System、Bottom Sheet、input boundary 和 reusable interaction patterns；Coffee Bean、Syrup Add-on、Decoration placement、Wall Decoration、Pick-up Point 与正式 mobile adaptation 仍由各自 Roadmap Phase 负责。

### 10.10 Atmosphere 方向

Atmosphere 属于装修系统的重要成长方向，但不是当前基础架构的核心。

已确认方向：

- 功能家具直接影响经营能力。
- 纯装饰主要贡献整体 Atmosphere。
- 同类装饰重复摆放应有递减收益或上限。
- 主题搭配可以提供额外效果。
- 系统应避免让玩家为了最高数值反复使用同一件家具。

具体 Atmosphere 算法、范围、主题组合和客群影响尚未确定。

为保留扩展空间，Furniture Data 应能够描述 Category、Theme Tags、Grid Footprint、Rotation、Surface Type、Interaction Anchors 和基础 Atmosphere 等信息。

### 10.11 店铺外观

外部装修可以包括：

- 外墙颜色和材质
- 店铺招牌
- 门窗和遮阳棚
- 户外灯饰
- 花盆、长椅、自行车和黑板菜单
- 门口地毯
- 节日装饰
- 户外座位或小花园

外观不应只存在于装修菜单中。顾客进店前的场景也应显示玩家选择的外部装修，让购买和布置具有实际存在感。

### 10.12 Save 与系统边界

装修存档至少需要表达：

- 已解锁的 Grid 区域、房间和楼层
- 每件已摆放家具的稳定 Instance ID、Definition ID、位置、旋转和楼层
- 自定义 Pick-up Point 与其绑定家具的相对 Surface Slot
- 已解锁家具和结构内容
- 外部装修选择

Furniture Footprint、Grid Occupancy 和可通行区域应从 Furniture Definition 与已保存布局重新计算，不作为唯一可信的重复存档数据。

Atmosphere、家具价格和具体 Pathfinding 实现可以独立演进。Furniture Definition 发生变化时，需要通过 Save Migration 或兼容规则保护已有布局，不能静默丢失家具或自定义 Pick-up Point。

## 12. 从 Design 到 Implementation

后续创建 implementation plan 时，应：

1. 明确本次目标和可验证结果。
2. 只选择本文档中与目标相关的系统。
3. 将未决定但会影响实现的问题先带回 planning task 确认。
4. 明确本次包含与不包含的内容。
5. 把功能拆成可独立验证的小步骤。
6. 为每一步定义 Play Mode、Console、数据和 Save 验收标准。
7. Implementation 完成后，把新确认的长期规则同步回本文档。

### 12.1 建议的系统边界

Implementation plan 应优先保持以下数据边界独立：

- **Character**：身份、Species、Breed、traits、关系和动态状态
- **Order**：订单状态、排队顺序、付款与材料预留
- **Recipe / Inventory**：配方、材料、商品与库存
- **Store Layout**：Grid、扩建区域、楼层和布局
- **Furniture / Interaction**：Furniture Definition、实例、表面与 Interaction Anchors
- **Time / Business Day**：营业时间、速度、打烊和日报
- **Save**：对上述系统状态进行版本化持久化，而不是拥有游戏规则

这些系统可以通过明确事件协作，例如：

- `CustomerEntered`
- `OrderPlaced`
- `IngredientsReserved`
- `OrderCompleted`
- `LayoutChanged`
- `BusinessDayEnded`
- `CharacterStateChanged`

事件名称只是 implementation plan 的示例，不要求直接采用相同代码命名。重点是避免订单、NPC、库存、装修和 Save 逻辑全部耦合在同一个组件中。

开发阶段和 phases 应在独立的 implementation plan 中制定，不写入本 design 文档。
